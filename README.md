# EFFEСOM · Контент-сервис — Этапы 1-2 (каркас)

Внутренний сервис для редакционного процесса EFFEСOM.
Реализованы **Этап 1** (устойчивый каркас) и **Этап 2** (UX и редакционный
процесс). AI-генерация, парсинг источников, внешние публикации и аналитика —
это этапы 3-5, они добавляются поверх этой базы.

## Что добавил Этап 4b (работа с найденными материалами)

- **Тема из выбранных материалов** (11.4.7, 11.15.1): в ленте «Материалы» и в
  карточке источника; направление и ключевые слова заполняются словарём правил
  (без AI); связь «тема ← материалы» хранится в новой join-таблице
  `topic_source_items` (раздел 9 ТЗ) — таблица `topics` не изменялась.
  Путь «инфоповод → тема → статья» работает как раньше.
- **Фильтры материалов**: источник, период дат, минимальная релевантность,
  статус — опциональные query-параметры, прежние вызовы не изменились.
- **Массовые действия** (без AI): скрыть, восстановить (скрытое → новое),
  отметить просмотренными; материалы с созданным инфоповодом не трогаются.
- **Ручной AI-анализ группы** (6.2.4-6.2.6): кнопка «Анализ группы (AI)» на
  отмеченных материалах → ПРЕДПРОСМОТР (выжимка, «почему важно», важность,
  варианты тем) — сам по себе ничего не сохраняет. Сохранение — только
  отдельным кликом «Создать инфоповод с анализом». Бюджет и журнал AI —
  из Этапа 3; AI-off отвечает «AI не настроен».
- **Досев промптов** стал аддитивным: при старте создаются только
  отсутствующие ключи (добавлен `group_analysis`); существующие промпты,
  их тексты и история версий не изменяются.
- Миграция: одна, `0006_stage4b` — только `topic_source_items`.

## Что добавил Этап 4a (мониторинг источников)

Реализован минимальный мониторинг по «Этапу 3» нумерации ТЗ (6.1-6.2, 11.4,
сущность SourceItem, планировщик 14.7):

- **Воркер** — отдельный сервис `worker` в docker-compose (тот же образ, что
  backend, `python -m app.monitor`). По умолчанию `MONITOR_ENABLED=false`:
  воркер запущен, но НИЧЕГО не парсит. Включение — в `.env` + перезапуск.
  Расписание — по «Частоте проверки» источника; «Вручную» = только кнопка.
- **Что парсится:** RSS/Atom — основной и надёжный сценарий; простые
  HTML-списки новостей — базовая поддержка. Сложные динамические страницы —
  сознательное ограничение этапа (Playwright не используется). Сайт целиком
  не обходится — только страница списка.
- **Правовые гарантии (раздел 2 ТЗ):** robots.txt уважается; закрытые и
  платные разделы не открываются (401/402/403 → «Доступ закрыт»); запросы
  анонимные с честным User-Agent, таймаутом и лимитом размера; полные тексты
  не сохраняются — заголовок, ссылка, дата, выдержка ≤1500 знаков.
- **Дедупликация:** уникальность URL на источник (индекс в БД) + hash
  содержимого — переопубликованный под другим адресом материал не плодится.
- **Релевантность** — словарь ключевых слов направлений EFFEСOM (обычные
  правила, без AI); балл виден в списке материалов.
- **Экраны:** «Материалы» (лента с действиями «Создать инфоповод» — без AI,
  «Анализ (AI)» — единственное AI-действие этапа, строго по клику,
  «Скрыть») и карточка источника («Проверить сейчас», найденные материалы
  с чекбоксами → один инфоповод из выбранных, история проверок, ошибки).
  Автоматически инфоповоды/темы/статьи НЕ создаются.
- **Миграция:** одна, `0005_stage4` — только таблицы `source_items` и
  `source_checks`; таблицы Этапов 1-3.2 не изменялись.
- **Самотест парсера:** `python3 scripts/parse_selftest.py` — RSS/Atom/HTML
  на локальных фикстурах, без сети и базы.
- Новые зависимости backend: `requests`, `beautifulsoup4` (закреплены).

## Что добавил Этап 3 (AI-генерация)

Реализован «Этап 2. Генерация статей» по нумерации ТЗ (разделы 6.6-6.9,
11.7, 11.12, 12, 14.11):

- **Абстрактный AI-провайдер** (`backend/app/ai.py`): OpenAI-совместимые API
  и Anthropic, без жёсткой привязки. Все настройки — только в `.env`
  (блок `AI_*`); ключ не хранится в коде, БД и интерфейсе.
  **AI-off режим:** если ключ не задан, сервис полностью работает,
  а AI-кнопки сообщают «AI не настроен».
- **Генерации** (карточка статьи → «AI-помощник», тема → «SEO-бриф (AI)»):
  SEO-бриф из темы за 1 клик, черновик статьи по брифу, версии для
  Дзен/VK/Telegram, «Улучшить текст», «Проверить факты», «Проверить
  юридические риски». Все результаты сохраняются **только как черновики**;
  финальный текст AI не трогает; перезапись существующего содержимого —
  только после подтверждения; повторный запуск блокируется до завершения
  первого.
- **Автопроверка качества** (6.9): AI лишь ПРЕДЛАГАЕТ отметки чек-листа
  (подпись «AI»); редактор и эксперт могут изменить любую; правило
  «нельзя в „Готова к публикации" при незакрытом чек-листе» и роли
  Этапа 2 не изменялись.
- **Промпты** (экран «Промпты», admin/editor): редактирование шаблонов,
  автоматическая история версий (версии не удаляются), тестовый запуск.
- **Бюджет и журнал** (14.11.7-8): каждый запрос пишется в `ai_requests`
  с токенами и стоимостью; при достижении `AI_DAILY_BUDGET_USD` /
  `AI_MONTHLY_BUDGET_USD` запросы приостанавливаются. Расход виден
  администратору на дашборде.
- Миграция: одна, `0003_stage3` (prompts, prompt_versions, ai_requests);
  таблицы Этапов 1-2 не изменялись.

**Важно про нагрузку.** Генерация выполняется синхронно (MVP): запрос
держит соединение до `AI_TIMEOUT_SECONDS` (nginx для `/api/ai/` держит
180 с; остальной API — прежние 60 с). Для массовой генерации и
мониторинга источников на следующих этапах ОБЯЗАТЕЛЕН вынос AI-задач в
фоновый worker с очередью (Redis + RQ/Celery, раздел 14.7 ТЗ) — текущая
схема рассчитана на ручной редакционный темп.

Как включить AI: в `.env` заполните `AI_PROVIDER` (openai | anthropic),
`AI_API_KEY`, `AI_MODEL` (и при необходимости `AI_BASE_URL` для
совместимых шлюзов), затем `docker compose up -d backend`.

**Обязательно заполните `AI_PRICE_INPUT_PER_1M` и `AI_PRICE_OUTPUT_PER_1M`**
реальными ценами выбранной модели (с сайта провайдера): по ним считается
стоимость в журнале `ai_requests`. При нулевых ценах расход учитывается
как $0 — и дневной/месячный бюджетные лимиты фактически не срабатывают.
Бюджет действует на все AI-запросы, включая тестовые запуски промптов.

## Миграции базы (Alembic)

Схема версионируется через Alembic (`backend/migrations`). При старте backend
автоматически докатывает базу до актуальной ревизии, ручной SQL не нужен:

- пустая база → создаётся схема Этапов 1-2 (ревизии `0001_stage1` → `0002_stage2`);
- база, созданная ранее через `create_all` (Этап 1 или Этап 2), распознаётся
  по имеющимся таблицам, помечается своей ревизией и дополняется недостающим —
  данные сохраняются.

> **Важно.** Миграцию существующей (старой) базы сначала проверяйте на копии,
> а не на боевых данных: снимите дамп, разверните его в отдельной базе,
> запустите backend на неё и убедитесь, что миграции применились и данные целы.
>
> ```bash
> docker compose exec db pg_dump -U effecom effecom > backup_до_миграции.sql
> docker compose exec db createdb -U effecom effecom_migration_test
> docker compose exec -T db psql -U effecom effecom_migration_test < backup_до_миграции.sql
> # укажите backend'у DATABASE_URL на effecom_migration_test и проверьте старт
> ```

Команды при разработке (из каталога `backend`, с установленными зависимостями):

```bash
alembic upgrade head                          # применить миграции
alembic revision --autogenerate -m "..."      # новая ревизия по моделям
alembic downgrade -1                          # откат на шаг
```

## Что входит в Этап 1

- **Backend** — FastAPI + SQLAlchemy + PostgreSQL.
- **Авторизация** — email + пароль, bcrypt, JWT; сессия истекает после
  `ACCESS_TOKEN_MINUTES` неактивности, при работе продлевается автоматически
  (`/api/auth/refresh`), абсолютный предел — `SESSION_MAX_HOURS`;
  блокировка после серии неудачных входов.
- **Роли** — администратор, редактор, эксперт, контент-менеджер, руководитель.
  Права проверяются на каждом endpoint.
- **CRUD** — источники, база знаний EFFEСOM, темы, статьи, пользователи.
- **Редакционный процесс** — машина статусов статьи (Черновик → На редактуре →
  На экспертной проверке → Готова к публикации → …) с правами по ролям.
- **Админ-панель** — React: дашборд, списки, карточка статьи с редактором,
  журнал безопасности. Разделы меню фильтруются по роли.
- **Журнал действий** — входы, неудачные входы, создание/изменение/удаление,
  смены статусов, IP.
- **Docker Compose** — Nginx (наружу) → backend → PostgreSQL (закрытая сеть).
- **Healthcheck** — `GET /api/health` + Docker healthchecks.

## Быстрый запуск

Требуется Docker и Docker Compose v2.

```bash
cp .env.example .env
# Заполните .env:
#   POSTGRES_PASSWORD  — openssl rand -base64 24
#   SECRET_KEY         — openssl rand -hex 32
#   ADMIN_PASSWORD     — пароль первого администратора (мин. 10 символов)

docker compose up --build -d
```

Панель: http://localhost (или порт из `APP_PORT`).
Вход — `ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env`.
Первичный администратор создаётся один раз при пустой базе.

### Чек-лист запуска

1. `.env` заполнен: `POSTGRES_PASSWORD`, `SECRET_KEY`, `ADMIN_PASSWORD` не пустые;
   `ADMIN_EMAIL` — на обычном домене (адреса на служебных доменах
   вроде `.local` отклоняются валидацией email при входе).
2. `docker compose up --build -d` завершился без ошибок.
3. `docker compose ps` — все три контейнера в состоянии `healthy`.
4. `docker compose logs backend | grep -i "миграции\|администратор"` —
   миграции применены, первичный администратор создан.
5. `curl http://localhost/api/health` → `{"status": "ok", "database": "ok"}`.
6. Вход в панель под `ADMIN_EMAIL`/`ADMIN_PASSWORD` работает.
7. Автоматически всё то же самое проверяет smoke-test (данные не изменяет):

```bash
./scripts/smoke_test.sh                    # адрес по умолчанию http://localhost
BASE_URL=https://content.example.ru ./scripts/smoke_test.sh
```

## Воспроизводимая сборка frontend (npm ci)

Версии зависимостей зафиксированы точно (без `^`), Docker-сборка использует
только `npm ci` — она требует `frontend/package-lock.json` и упадёт без него.
Lock-файл генерируется один раз в окружении с доступом к npm-реестру
и коммитится в репозиторий:

```bash
cd frontend && npm install --package-lock-only
```

## Запуск для разработки (без Docker)

```bash
# Backend (нужен запущенный PostgreSQL, DATABASE_URL в .env)
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload            # http://localhost:8000, docs: /api/docs

# Frontend
cd frontend
```

## Развёртывание в production (кратко)

Этапы 1-2 готовят контур из раздела 14 ТЗ; на боевом сервере дополнительно:

1. `ENVIRONMENT=production` в `.env` (скрывает `/api/docs`).
2. HTTPS: поставить перед `frontend` Caddy/Traefik или выпустить сертификат
   Let's Encrypt и терминировать TLS в Nginx; наружу открыть только 443 (80 → redirect).
3. `CORS_ORIGINS=https://ваш-домен`.
4. SSH только по ключам, firewall: открыты только 80/443 и SSH для админов.
5. Backup PostgreSQL ежедневно, хранение 14–30 дней вне сервера:
   `docker compose exec db pg_dump -U effecom effecom > backup_$(date +%F).sql`
   (восстановление: `psql -U effecom effecom < backup.sql`); тест восстановления — ежемесячно.
6. Разные `SECRET_KEY`, пароли и `.env` для dev/staging/production.
